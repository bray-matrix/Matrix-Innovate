# Innovation Hub v1.6.12 — Department authorization correction

## Production evidence and root cause

The authenticated production session diagnostic returned HTTP 200 with
`roles: ["platform_administrator"]`. This is the authorization shape retained
after verified Platform launch and local signed-session exchange, not a raw JWT
capture. No tokens, credentials, identity identifiers, names, or email addresses
were collected for diagnosis.

v1.6.11 recognized only `admin`, `superadmin`, `super_admin`, and `super admin`
(case-insensitive). Both the frontend and backend rejected the actual
`platform_administrator` value. Platform already supplied sufficient
authoritative information; Innovation Hub's allowlists were incorrect.

## Correction

- Added the observed `platform_administrator` role to both department-management
  allowlists, retaining existing compatibility aliases.
- Bumped frontend/API package versions and application metadata to v1.6.12.
- Kept signature verification, signed-session propagation, and server-side 403
  enforcement unchanged. No second role system, identity hard-coding, bypass,
  Platform change, schema change, or production mutation.
- Categories, Jira, Guided Interview, scoring, and Project workflows unchanged.
  The existing metadata assertions in the Jira test file were updated only for
  the application version.

## Validation

- Department integration tests: 4/4 passed using the observed role contract.
  Initialization, Add, Rename, Deactivate, Reactivate, stable IDs, normalized
  duplicate rejection, reference propagation, inactive new-selection exclusion,
  historical retention, reactivation, and read-only fallback covered.
- Launch/session tests: 62/62 passed. Locally signed fixture launch with the
  exact captured role survives verification, cookie minting, and session reads.
- Missing roles, synthetic `User`, unknown role, and near-match
  `platform_administrator_extra` receive 403 for initialization, add, rename,
  deactivate, and reactivate. These denied roles are negative fixtures, not
  claims about Platform's ordinary-user role vocabulary.
- Browser-only session/settings fixtures verified all maintenance controls
  visible for `platform_administrator`; controls hidden for no roles and
  `unknown_platform_role`. Categories stayed read-only. Rename/deactivate/
  reactivate request bodies were also checked using intercepted responses.
  Browser fixtures do not prove backend persistence; integration tests above
  independently exercise the development database.
- Library, API, and frontend typechecks passed. API and frontend builds passed;
  frontend build emitted source-map/chunk-size warnings. Both workflows running.
  The standalone frontend build requires PORT and BASE_PATH, supplied on retry.

## Post-publish acceptance boundary

Real Matrix Platform authentication could not be reproduced in the development
browser under the existing authentication limitation. Validation used the exact
production-observed role contract, not another guessed administrator role.
After manual Git Sync and Publish, a fresh real Platform launch must confirm
visible controls and successful Add/Rename/Deactivate/Reactivate. A real
non-administrative Platform session must confirm hidden controls and HTTP 403
on direct mutations; its actual role value has not yet been captured.
