# Primary Owner picker — Matrix Platform handoff (proposed contract)

**Status:** Dependency proposal, not an existing Platform API. Matrix Innovation Hub v1.5.0 retains free-text Primary Owner until Platform supplies an authorized directory contract. Platform source and its exact user-service/API contract were not available for inspection; endpoint paths, field names, token mechanism, and tenancy model below require Platform confirmation.

## Existing Hub boundary

Hub receives a Platform launch JWT in the URL fragment, removes it from the URL, and exchanges it once at `POST /matrix/session`. The API verifies issuer, audience, signature against discovery/JWKS and expiry, then issues its **own** short-lived HttpOnly `matrix_session` cookie. `/api` business routes require this cookie; the locally signed session contains `sub`, `name`, and `email`, **not** directory authorization or a tenant claim. See `artifacts/api-server/src/matrix/auth.ts`, `matrix/platform.ts`, and `app.ts`. Today promotion accepts a free-text `primaryOwner` (`POST /api/initiatives/:id/promote`), saved in `projects.primary_owner`; initiative `business_owner`/`executive_sponsor` are also free text and can prefill it. A logged-in user's identity or a name string is not proof of a proposed owner's current eligibility.

## Contract requested from Platform

- **Search:** propose `GET /platform/.../owner-candidates?application=matrix-innovation-hub&q=...&active=true&eligible=true&limit=...&cursor=...` (illustrative path only). Return authorized candidates in the caller's tenant/application scope. Search normalized display name and email/UPN (case-insensitive, partial match), support empty-query bounded initial results if allowed, deterministic ordering, bounded page size and opaque continuation cursor; do not dump the full directory. Response: `items`, `nextCursor` (null at end). Document minimum query length, rate limits and whether aliases are searched.
- **Resolve/validate:** propose `GET /platform/.../owner-candidates/{stableId}?application=matrix-innovation-hub` or a corresponding `POST .../resolve` for exact IDs. Must independently check current active status, application eligibility, and tenant scope **at save time**, not rely on search results or client-supplied labels. Return `id` (immutable, non-recycled Matrix user ID or tenant-qualified Entra object ID; specify namespace/tenant), `displayName`, `email` and/or `upn` where available (nullable if absent), `active`, `eligibleForApplication` (boolean or explicit authorization state), and tenant/scope identifier as appropriate. The server must distinguish not found/out of scope, inactive, ineligible, and Platform-unavailable outcomes without leaking cross-tenant identity details to clients. Define whether eligibility means an authorized Hub user, assignable owner, or a separate role; agree on the exact owner policy before wiring the picker.
- **Authentication:** Hub browser calls only its session-protected Hub API. Hub API validates its local session, then calls Platform server-to-server over HTTPS using a **Platform-defined delegated, signed exchange/token** bound to the authenticated Platform `sub`, Hub application audience, tenant and directory-read scope, with short expiry; Platform authenticates the Hub service and enforces the caller's authorization and tenant on both search and resolve. Platform must specify the exchange endpoint, signing/trust keys, token audience, scopes and rotation. This is a requested capability, **not an existing Hub endpoint or confirmed Platform flow**. Do not forward the Hub `matrix_session` cookie, its `SESSION_SECRET`, or the one-time launch token as a Platform API credential; do not add Graph credentials, a second Entra integration or a local employee directory. If Platform already supports a suitable delegated flow, reuse it instead of adding another.
- **Tenancy:** Platform must supply/derive authoritative tenant context for both the caller and candidate. Hub's current session has no tenant claim, so do not infer tenant from email domain or accept a client-provided tenant as authority. The signed exchange and resolve response must provide enough scope to enforce same-tenant selection (or an explicitly permitted cross-tenant policy). Hub must fail closed if the tenant cannot be established.

Platform may already have user records, app assignments and search services suitable for reuse; likely only a small **scoped search + exact resolve/validate API and/or delegated exchange** is needed. This cannot be confirmed without Platform source/API review. Platform owns the authoritative identity, assignment policy, and contract documentation.

## Hub adoption after contract approval

Persist `primary_owner_id` (stable, namespaced/tenant-qualified reference) plus `primary_owner_display_name` snapshot on projects, optionally email/UPN snapshot for presentation; never use name/email as identity. Keep the current `primary_owner` text for compatibility during an additive migration and update reporting/UI reads deliberately. The save/promote server must resolve the submitted ID and enforce active, eligible, application and tenant policy immediately before insert/update, take display snapshot from the Platform response (not request body), and reject missing/stale/inactive/ineligible/out-of-scope IDs with a clear 4xx validation/conflict response; return a retriable 503 when Platform cannot validate, never silently accept text. Recheck on subsequent owner changes. Historical free-text values stay as **unverified legacy** with null ID until explicitly selected/confirmed by a user; do not auto-match names or silently assign IDs. Existing project reads remain displayable, but any changed/new owner must be controlled; define handling of unrelated edits to legacy projects separately without silently converting the owner. Prefilled initiative names remain suggestions only, never selected identities.

## Acceptance criteria for replacing free text

1. Platform publishes the actual versioned search/resolve schema and delegated auth contract; Hub can search paginated candidates by name/email/UPN and resolve by stable ID, with only active, application-eligible, appropriately scoped people selectable.
2. Unauthorized, expired, or wrong-audience delegated requests fail; a caller cannot search/resolve another tenant or escalate scope via query/body. Neither launch JWT nor Hub cookie/session secret is sent as directory credentials.
3. Hub picker is keyboard-accessible, shows name plus email/UPN for disambiguation, and submits ID rather than typed text. Duplicate names remain distinguishable.
4. Hub server revalidates on project create/promotion and owner update; changed, deleted, deactivated, revoked, or cross-tenant candidates cannot be saved even if present in a stale picker result. Platform outage blocks new owner assignment with an explicit error.
5. New records store stable ID and display snapshot; legacy free-text records remain readable and marked unverified, never auto-resolved. Migration preserves existing values and reports; explicit reselection produces a verified ID.
