## Jira reads: before versus after

Before: every Linked Work GET read each linked issue live; the general Refresh Jira button let ordinary users force additional reads.

After: normal Refresh Jira removed. Linked Work uses persisted selected-issue metadata; opening it refreshes snapshots older than five minutes. React Query considers the Hub response fresh for 60 seconds and does not refetch on window focus. Ordinary renders do not trigger Jira reads. Explicit search and link confirmation still perform their necessary Jira reads.

Successful snapshots are stored in PostgreSQL. Failed refresh attempts preserve the last known snapshot and suppress retries for one minute. An in-process promise map coalesces concurrent requests, while an atomic database attempt claim limits duplicate reads across server instances. Reads use four workers maximum and an eight-second page-resolution budget. There is no background polling or broad synchronization.

Three additive nullable cache columns were applied to the development schema only. Production adoption remains part of the normal manual Publish schema process; no startup DDL or production migration script was added.

Jira remains authoritative and external operations remain read-only. Local links/cache rows are Hub data, not Jira writes.
