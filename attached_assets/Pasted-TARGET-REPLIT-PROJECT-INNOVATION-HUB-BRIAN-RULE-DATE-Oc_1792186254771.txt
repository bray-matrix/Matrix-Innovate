============================================================
1. OBJECTIVE
============================================================

Implement the first bounded release of the Innovation Hub
usability improvements identified in the October 16, 2026
UX assessment.

The goal is to make Innovation Hub easier to understand,
navigate, and use, particularly when creating and managing
projects.

Preserve the existing architecture, integrations, records,
and security model.

This release focuses on:

1. Simplified primary navigation
2. Clearer terminology
3. Improved project creation
4. Editing existing project details
5. Better workflow guidance
6. Consistent project health presentation
7. Honest labels and clearer Save/Cancel behavior

Do not redesign the application or introduce new governance
requirements.

============================================================
2. APPROVED BUSINESS DECISIONS
============================================================

DECISION 1 — INITIATIVES VS PROJECTS

An Initiative evaluates whether an idea or opportunity
is worth pursuing.

A Project manages work that has been selected for planning
or execution.

IMPORTANT:

Brian has NOT approved unrestricted direct project creation
as the preferred long-term business workflow.

His concern is that bypassing the Initiative process could
produce poorly defined projects without sufficient scope,
business justification, or expected outcomes.

For this release:

- Preserve existing direct project creation.
- Preserve Initiative-to-Project creation.
- Do not introduce a mandatory Initiative prerequisite.
- Do not change API authorization or governance rules.
- Make the Initiative-first path the recommended experience.
- Explain that the Initiative process helps establish scope,
  expected outcomes, and business justification.
- Present direct project creation as an alternative for work
  that is already sufficiently defined.
- Do not imply that direct creation has been permanently
  approved as the preferred organizational policy.

We will evaluate whether additional project-intake controls
are appropriate after usability testing.

DECISION 2 — APPROVAL REQUIREMENTS

Creating a Project from an Initiative does not require
the Initiative to have Approved status.

Preserve this behavior.

Creating a Project does not automatically authorize
funding, production deployment, or implementation.

Do not introduce new approval gates.

DECISION 3 — ORGANIZATIONS, CLIENTS, PROGRAMS

Use these working definitions:

Organization:
An optional parent company or corporate entity.

Client:
An individual Matrix customer/account.

Program:
A grouping of related projects.

These definitions are provisional.

Do not restructure the database, merge records, or enforce
new relationships.

Use brief contextual explanations where helpful.

DECISION 4 — PROJECT OWNERSHIP

Project Owner means the individual accountable for
successful project delivery.

In many Matrix projects, the Project Owner will also be
the Project Manager.

THIS IS EXPECTED AND ACCEPTABLE.

Do not create a separate Project Manager field.

Executive Sponsor:
Provides leadership sponsorship and helps remove obstacles.

Assigned Resources:
People or departments performing project work.

Preserve the existing data model.

Do not invent new project sponsor fields or reinterpret
Supporting Owners as formal sponsors.

============================================================
4. PROJECT CREATION
============================================================

Simplify the existing direct project-creation experience.

The initial form should emphasize:

REQUIRED:
- Project name
- Project owner
- Work type

OPTIONAL:
- Description / intended outcome
- Client

ADDITIONAL DETAILS:
- Organization
- Program
- Supporting owners
- Target date
- Other existing optional fields

Preserve existing defaults where appropriate.

Do not automatically classify every new project as
Internal Technology.

Make the work-type selection understandable for business
users across Matrix.

Use clear required-field indicators.

Provide field-level validation and useful error messages.

Do not introduce a multi-page wizard unless technically
necessary.

Do not remove existing fields or capabilities.

Do not fabricate project scope, owners, dates, or
business justification.

IMPORTANT:

Before simplifying the creation form, ensure users can
edit deferred information after the project is created.

5. EDIT EXISTING PROJECT DETAILS
============================================================

This is a critical requirement.

Currently, users cannot edit several fundamental project
attributes from the normal Project Detail interface.

Implement a clear "Edit project details" action.

Support editing existing fields including:

- Project name
- Description
- Primary owner
- Supporting owners
- Work type
- Client
- Organization
- Program
- Target date, where supported by the existing contract

Use the existing API/update architecture wherever possible.

Do not change project IDs.

Do not lose:

- Linked initiatives
- Jira links
- Milestones
- Risks
- Approvals
- Resources
- Readiness assessments
- Historical relationships

Preserve existing validation and authorization.

Ensure Cancel discards unsaved edits.

Validate optional relationship clearing and unchanged-field

Do not introduce a new schema unless an unavoidable
technical requirement is identified and reported first.

============================================================
6. PROJECT NEXT STEPS
============================================================

After creating a project, provide clear next actions.

Examples:

1. Confirm project scope and ownership.
2. Add the next milestone.
3. Assign resources or identify department needs.

These should be contextual actions linking to existing
capabilities.

Do not automatically create milestones, assignments,
approvals, or readiness requirements.

Do not impose new project-governance obligations.

The user should immediately understand:

- What was created
- What information was saved
- What remains optional
- What to do next

============================================================
7. INITIATIVE-TO-PROJECT WORKFLOW
============================================================

Preserve the existing Initiative promotion architecture.

Change confusing user-facing terminology.

Prefer:

"Create linked project"

instead of:

"Promote"

Explain that:

- The Initiative remains intact.
- A separate Project is created.
- The Project retains its relationship to the Initiative.
- Existing supported Jira links remain associated.
- Project creation does not itself constitute formal approval.

Clearly distinguish:

Develop an idea
→ Save Initiative
→ Evaluate Initiative
→ Create linked Project
→ Manage Project

This represents the recommended business workflow.

Do not imply every step is a mandatory technical gate.

Do not change Initiative scoring, interview convergence,
status transitions, or duplicate-project protections.

11. SAVE / CANCEL / DELETE
============================================================

Improve consistency across the affected workflows.

For multi-field editing:

Save = persist changes.

Cancel = discard unsaved changes.

For existing immediate-save controls:

Clearly indicate that changes save immediately.

Where Cancel actually returns to a previous interview
screen, use accurate wording such as:

"Return to interview"

Do not alter private interview autosave behavior.

Move prominent destructive Project Delete actions into
an appropriate secondary action area.

Preserve existing deletion authorization and behavior.

Explain potential consequences before deletion.

Do not modify database cascade rules.
