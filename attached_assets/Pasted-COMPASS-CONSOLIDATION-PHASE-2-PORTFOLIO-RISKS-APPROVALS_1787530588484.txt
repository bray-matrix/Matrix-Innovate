4. GO-LIVE READINESS
--------------------------------------------------

Reuse and extend the existing Validation architecture rather than building an unrelated checklist engine.

Create a project-specific Go-Live Readiness capability.

A project may have one or more readiness assessments.

Add entities as appropriate using the existing validation/checklist patterns.

Each readiness assessment should support checklist items with:

- category
- requirement
- owner
- status
- notes
- required boolean
- sequence/order

Status:
- Not Tested
- Pass
- Fail
- Not Applicable

Readiness categories should initially support:

- Requirements
- Development
- Testing
- Data
- Operations
- Client
- Security / Compliance
- Production
- Training / Documentation

Do not hard-code the architecture so these categories cannot change later.

Calculate a readiness summary:

- Ready
- At Risk
- Not Ready
- Not Started

Rules should be deterministic and server-side.

At minimum:

NOT READY:
one or more required checklist items = Fail

AT RISK:
required items remain Not Tested near target/go-live date

READY:
all required items Pass or Not Applicable

NOT STARTED:
no readiness work has begun

Add Go-Live Readiness to Project Detail.

6. PORTFOLIO HEALTH
--------------------------------------------------

Implement deterministic server-side project health calculation.

Do not make AI responsible for health.

Recommended initial rules:

OFF TRACK if:
- any open Critical risk
OR
- required Go-Live Readiness item has failed near target date
OR
- critical/stage-gate milestone significantly overdue

AT RISK if not Off Track and:
- any open High risk
OR
- milestone overdue
OR
- pending critical approval
OR
- readiness is At Risk
OR
- target date is approaching with incomplete milestones

ON TRACK otherwise for active projects with sufficient data.

UNKNOWN if insufficient data exists.

Preserve a manually stored health field only if required for compatibility, but clearly distinguish calculated health from manual override.

If adding manual override:
- store reason
- store who changed it
- store timestamp

Do not silently overwrite an explicit manual override.
