TARGET REPLIT PROJECT: INNOVATION HUB

- Matrix Platform
- Finance Hub

CURRENT ACCEPTED PRODUCTION BASELINE:
Innovation Hub v1.6.13

OBJECTIVE:
Make the Innovation Hub DEVELOPMENT environment usable for authenticated preview without requiring a production publish for every meaningful UI/functional review.

Architecture must continue to use Matrix Platform for identity, authentication, authorization, Microsoft Graph access, and shared credentials.

DO NOT create a separate Microsoft Entra application registration, Graph credential set, client secret, API key, or independent Microsoft authentication architecture inside Innovation Hub.

============================================================
1. REQUIRED ARCHITECTURE
============================================================

Innovation Hub remains a Matrix Platform child application.

Target development authentication flow:

Innovation Hub Development
→ Matrix Platform development/authentication capability
→ authenticated Matrix identity
→ Innovation Hub development session

The authenticated identity should use the same stable Platform identity concepts used in production wherever practical, including:

- stable user subject/ID
- name
- email
- Platform roles/capabilities
- authorization context

The verified production administrative role contract remains:

platform_administrator

Do not invent replacement roles such as:

admin
superadmin
super_admin

Authorization must remain server-side.

============================================================
2. MICROSOFT / GRAPH CREDENTIAL RULE
============================================================

Innovation Hub must NOT directly own Microsoft Graph credentials.

Where Innovation Hub needs Matrix user/directory information, the intended architecture is:

Innovation Hub
→ Matrix Platform shared user/directory capability
→ Microsoft Graph

Platform owns the Microsoft credentials.

Innovation Hub consumes a bounded Platform service/API/SDK contract.

Do not duplicate secrets into Innovation Hub Replit Secrets.

Do not create a second Graph connection simply because it would be faster.

============================================================
3. FIRST TASK — INSPECT EXISTING ARCHITECTURE
============================================================

Before adding new authentication code, inspect the existing Innovation Hub and Matrix Platform integration already present in this project.

Identify:

- current production launch-token/session flow
- existing Matrix Platform SDK usage
- current environment detection/configuration
- current production callback/launch URLs
- how production session identity is established
- whether Platform already supports any development/preview launch flow
- whether an existing Platform endpoint or SDK function can be reused for development authentication
- whether current development failures are caused by redirect URL, audience, issuer, cookie/domain, launch-token, or environment assumptions

Reuse existing architecture wherever possible.

Do not replace a working production authentication design.

============================================================
4. DEVELOPMENT AUTHENTICATION REQUIREMENT
============================================================

Implement a supported development authentication approach that lets Brian open the Replit development preview and authenticate as his real Matrix identity.

Preferred order:

A. Reuse/extend an existing Matrix Platform development launch capability if one already exists.

B. If Platform needs a small addition to support development child-app launches, document exactly what is required in Matrix Platform. DO NOT modify Matrix Platform from this Replit project.

C. Only if A/B are not currently possible, implement a tightly controlled DEVELOPMENT-ONLY fallback inside Innovation Hub.

Any fallback must:

- be impossible to activate in production
- fail closed if environment cannot be positively identified as development
- never use a generic shared admin password
- never create unrestricted anonymous access
- clearly identify the simulated/authenticated subject
- preserve server-side authorization checks
- be easy to remove once Platform development launch is available

Do not build a casual "skip auth" switch.
